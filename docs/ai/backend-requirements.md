# CampusPolio 백엔드 요구사항

팀 최종 정책 반영 · 2026-11-10

## 공통 응답과 목록

- 인증이 필요한 요청에 로그인 정보가 없으면 `401`을 반환한다. 공개 프로젝트와 공개 포트폴리오는 비로그인 상태에서도 조회할 수 있다.
- 비공개 리소스의 열람 권한이 없는 요청에는 `404`를 반환해 존재 여부를 숨긴다. 로그인한 사용자가 프로젝트 삭제·공개 전환이나 포트폴리오 수정·삭제를 요청했으나 해당 권한이 없으면 `403`을 반환한다.
- 소프트 삭제된 프로젝트·포트폴리오·계정은 모든 조회와 검색에서 제외한다. 공개 목록, 내 목록, 포트폴리오에 연결된 프로젝트 조회, 팀원 초대용 닉네임 검색에도 적용한다.
- 페이지 크기는 프로젝트 9개, 포트폴리오 6개로 한다.

## 계정과 인증

### 로그인과 대학 인증

- Google 로그인은 계정의 이메일 도메인과 관계없이 허용한다. 프론트엔드와 백엔드는 동일한 Google 클라이언트 ID를 사용한다.
- 대학 인증은 로그인 후 별도의 `.ac.kr` 이메일 주소를 입력하고 인증 코드를 확인하는 흐름이다. 인증에 성공하면 해당 계정의 `universityVerified`를 `true`로 설정한다.
- Google 로그인 이메일과 대학 인증 이메일은 별개로 다루며, 두 주소가 일치하는지 검사하지 않는다.
- 닉네임은 필수이며 계정 간에 중복될 수 없다. 프로젝트에 팀원을 초대할 때 이 닉네임으로 상대를 검색한다.

### 회원 탈퇴와 복구

- 탈퇴한 계정은 소프트 삭제한다. 탈퇴 후 30일 이내에 같은 Google 계정으로 다시 로그인하면 계정과 프로젝트·포트폴리오·멤버 관계·북마크를 복구한다.
- 30일을 넘기면 이전 계정은 영구 비활성 상태가 된다. 이때 같은 Google 계정으로 접속하면 새 계정으로 가입하며 이전 데이터를 복구할 수 없다.
- 탈퇴한 사용자가 프로젝트의 `OWNER`이고 `MEMBER`가 남아 있으면 가장 오래된 `MEMBER`에게 소유권을 넘긴다. 남은 `MEMBER`가 없으면 프로젝트를 소프트 삭제하고 30일 이내 복구할 수 있게 한다.
- 탈퇴한 사용자가 `MEMBER`인 프로젝트에서는 해당 사용자의 멤버 관계를 제거한다.

## 프로젝트

### 임시저장과 발행

- 로그인한 사용자는 대학 인증 전에도 `DRAFT` 프로젝트를 만들 수 있다. 생성자는 프로젝트의 `OWNER`가 된다.
- 발행은 `OWNER`이면서 `universityVerified`가 `true`인 사용자에게 허용한다. 제목과 썸네일이 필수이며, 본문(`content`)은 30자 이상 50,000자 이하여야 한다.
- 같은 임시저장 프로젝트를 다시 열어 이어서 작성한 뒤 발행할 수 있도록, 조회할 때 현재 작성 상태와 공개 여부를 제공하는 방향을 제안한다. 발행한 프로젝트의 공개 여부는 `OWNER`가 변경할 수 있다.

### 공개·비공개 조회와 검색

- 공개 프로젝트는 비로그인 사용자도 열람할 수 있다. 비공개 프로젝트는 `OWNER`와 해당 프로젝트의 `MEMBER`만 열람할 수 있으며 그 외 사용자에게는 `404`를 반환한다.
- 검색은 키워드, 태그, 최신순·조회수순 정렬을 지원하며 한 페이지에 9개를 반환한다. 검색 결과에는 공개 프로젝트만 포함한다.
- 같은 사용자의 반복 열람에서도 조회수가 증가할 수 있다.

### 작성자와 팀원의 권한

프로젝트마다 `OWNER`는 1명이다. 팀원 초대는 `OWNER`만 요청할 수 있으며 프로필 닉네임으로 초대 대상을 검색한다.

| 동작 | OWNER | MEMBER |
|---|---|---|
| 비공개 프로젝트 조회 | 가능 | 가능 |
| 본문·태그 수정과 파일 업로드 | 가능 | 불가 |
| 팀원 추가·제거 | 가능 | 불가 |
| 공개·비공개 전환 | 가능 | 불가 |
| 프로젝트 삭제 | 가능 | 불가 |

### 태그

- 입력한 태그를 소문자로 바꾸고 공백은 하이픈(`-`)으로 바꾼다. 이 규칙에 따른 하이픈은 허용하며 그 외 특수문자는 허용하지 않는다.
- 정규화한 태그는 프로젝트 안에서 중복될 수 없다. 프로젝트당 최대 10개, 태그 하나당 최대 10자다.

### 파일과 이미지

- 파일은 S3에 저장하고 S3 키로 식별한다. 서버가 발급한 S3 서명 URL(presigned URL)은 5분 동안 유효하다.
- PNG·JPG 파일만 허용하며 파일 하나당 최대 100MB다. 요청에 적힌 `Content-Type`과 실제 파일을 서버가 판별한 MIME 형식을 함께 확인한다.
- 업로드한 뒤 24시간 동안 프로젝트에 연결되지 않은 파일은 예약 작업으로 자동 삭제한다.
- 연결된 파일을 삭제하면 S3에서 즉시 제거한다. 프로젝트를 직접 삭제하면 해당 프로젝트의 S3 파일과 북마크도 삭제한다.
- 프로젝트 본문과 업로드 파일을 표시하는 경로에 XSS 방어를 적용한다.

## 포트폴리오

### 생성과 공유 주소

- `universityVerified`가 `true`인 사용자가 생성할 수 있으며 제목은 필수다. 생성 응답에는 `portfolioId`와 `slug`를 포함한다.
- 공유 주소에 쓰는 `slug`는 제목에서 자동 생성한다. 소문자로 바꾸고 공백을 하이픈으로 바꾸며 특수문자를 제거한다. 중복되면 숫자를 붙인다.
- 제목을 바꿔도 기존 `slug`를 유지한다. 삭제된 포트폴리오의 `slug`는 재사용하지 않는다.

### 조회와 공개 전환

- 공개 포트폴리오는 로그인 없이 `slug`로 열 수 있다. 비공개 포트폴리오는 소유자만 열람할 수 있으며 다른 사람의 조회에는 `404`를 반환한다.
- 상세 진입 시 포함된 프로젝트 목록을 조회한다. 비공개 프로젝트는 포트폴리오에 표시하지 않는다.
- 공개하려면 공개 프로젝트가 하나 이상 필요하다. 포함한 프로젝트가 모두 비공개가 되면 포트폴리오도 자동으로 비공개로 전환한다.

### 수정·삭제와 프로젝트 구성

- 소유자만 제목·설명·썸네일·공개 여부를 수정하거나 포트폴리오를 삭제할 수 있다. 다른 로그인 사용자의 수정·삭제 요청에는 `403`을 반환한다.
- 자신이 `OWNER`이거나 `MEMBER`로 참여한 프로젝트만 추가할 수 있다. 중복 없이 최대 50개를 담을 수 있으며 표시 순서를 바꿀 수 있다.
- 포트폴리오에서 프로젝트를 제거하거나 포트폴리오를 삭제하면 연결만 끊는다. 원본 프로젝트는 유지한다.

## 호출 제한

비로그인 요청은 IP, 로그인 요청은 사용자 ID를 기준으로 집계하며 Redis에 기록한다. 슬라이딩 윈도우 또는 토큰 버킷 방식으로 짧은 순간의 호출 증가를 허용한다. 중요한 API에는 더 강한 제한을 적용하고, 실패가 반복되면 임시 차단한다.

| 영역 | 제한 |
|---|---|
| 일반 API · IP 기준 | 1분에 60회 |
| 일반 API · 사용자 기준 | 1분에 120회 |
| 검색 | 1분에 120~180회 |
| 로그인 | 1분에 10회 |
| 인증 코드 발송 | 10분에 3회 |
| 인증 코드 검증 | 10분에 10회 |
| S3 서명 URL 발급 | 10분에 10회 |
| 프로젝트 생성 | 1시간에 30회 |

## 화면 연동을 위한 협의 요청

- 내 정보·내 프로젝트처럼 본인 기준 요청은 **인증 쿠키로 로그인한 계정을 식별**하는 방향을 제안한다. 로그인과 내 정보 응답에는 사용자 식별 정보, 이메일, 대학 인증 상태가 필요하다.
- 화면 이동과 새로고침 후에도 인증이 유효하면 **로그인 상태를 유지**할 수 있어야 한다. Access Token이 만료돼도 재발급에 성공하면 원래 요청을 이어갈 수 있게 한다. 재발급 불가와 일시적인 서버 장애는 구분해 각각 다시 로그인하거나 다시 시도하도록 안내한다. 쿠키 적용 범위·유효기간·갱신 실패 응답은 연동 계약에서 정한다.
- **로그아웃**하면 Refresh Token을 폐기하고 인증 쿠키를 삭제한다. 진행 중인 갱신과 로그아웃이 겹쳐도 화면 이동이나 새로고침 후 비로그인 상태를 유지할 수 있어야 한다.
- **대학 인증** 화면에서 만료와 재발송 시간을 정확히 안내할 수 있도록 실제 메일 발송 방식, 코드 만료 시각과 재발송 가능 시각, 잘못된 코드·만료·횟수 초과의 구분 방법을 명세에 포함해 달라고 요청한다.
- **내 프로젝트와 포트폴리오 선택 목록**에서 제목·요약·썸네일·태그·상태·내 역할을 한 번에 받는 방식을 제안한다. 제목·요약·태그 검색, 선택한 태그 모두 포함, 최초 발행일 기준 최신순, 제작 연도·학기·학과 저장과 필터는 기존 화면 요구로 전달하고 세부 계약을 합의한다.
- **공개 프로젝트의 수정 내용**을 저장하면 상세에 바로 반영하고, 편집을 다시 열면 저장 내용과 첨부를 복원하는 흐름을 제안한다. 이를 위해 파일 식별 정보, 이름·형식·크기, 열람 URL 발급 방법이 필요하다. 권한 변경과 URL 만료 시 화면에서 사용할 오류 응답도 합의한다.
- **포트폴리오 정보·선택 프로젝트·순서**를 한 번의 저장으로 반영하는 방식을 제안한다. 저장 중 일부만 반영되거나 응답 유실 후 다시 시도할 때 중복 생성되는 문제를 막기 위해서다. 연결 목록 편집에 필요한 정보의 범위와 자동 비공개 전환 사유를 소유자에게 전달하는 방식도 합의한다.
- **프로필**의 첫 저장에서도 입력한 내용을 한 번에 반영할 수 있게 제안한다. 닉네임 중복을 구분하고, 선택 항목을 그대로 둘 때와 비울 때의 요청 형태를 합의한다.
- **목록 응답**에는 페이지 정보와 전체 건수를, **오류 응답**에는 화면에서 원인을 구별할 수 있는 정보와 호출 제한 시 재시도 안내에 필요한 정보를 제공해 달라고 요청한다.
- **AI 리뷰**에서 현재 서버가 분석하는 자료, 실행·결과 열람 권한, 결과 보관과 재시도 방식을 확인한다.

## 확인이 필요한 정책 경계

- 갱신할 때 이전 토큰을 폐기하는 **Refresh Token Rotation**을 8주 계획에서 의도적으로 제외했는지 확인한다. 현재 명세는 재발급 시 새 토큰 발급을 설명하므로, 이전 토큰의 폐기와 재사용 처리도 함께 명시할 필요가 있다.
- **계정 복구 시 프로젝트 소유권**이 어떻게 되는지 정한다. 이미 팀원에게 소유권을 넘긴 뒤 이전 `OWNER`가 30일 이내에 복귀하는 경우에도 프로젝트당 `OWNER` 1명 규칙을 지켜야 한다. 복구 기간에 닉네임이 다시 사용된 경우의 처리도 정한다.
- **탈퇴로 삭제된 프로젝트의 파일과 북마크**를 복구 기간에 어떻게 보존하고 언제 정리할지 정한다. 프로젝트 직접 삭제의 정리 규칙을 탈퇴에 따른 소프트 삭제에도 적용하면 30일 복구 대상이 사라질 수 있다.
- 비로그인 사용자가 **비공개 주소를 직접 열었을 때** `401`과 존재를 숨기는 `404` 중 어떤 응답을 우선할지 정한다. 비공개 프로젝트의 팀원 열람 권한을 `DRAFT`에도 적용하는지 확인한다.
- **발행된 프로젝트만 포트폴리오에 연결**하는 기존 화면 요구를 적용할지 확인한다. 프로젝트 삭제·연결 제거로 공개 가능 프로젝트가 0개가 된 경우에도 자동 비공개로 전환하는지 확인한다.
- **검색 제한의 확정값**, 일반 제한과 기능별 제한을 함께 적용할 때의 우선순위, 임시 차단 기준을 정한다.
