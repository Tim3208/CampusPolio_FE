### P0 · 인증과 접근 제어

#### AUTH-01 · 로그인 유지, 본인 식별, 재발급과 로그아웃

- [ ] **BE 선합의** — login/refresh/logout의 `200` 응답은 있지만 쿠키 속성·만료 오류·회전/폐기·실패 응답이 없다. `GET /api/users/me`는 세션 설명과 필수 `userId`가 혼재하고 FE는 query를 생략한다. 로그인·프로필·포트폴리오·대학 인증·탈퇴에서 쿠키와 query의 역할을 확정하고, 동일 Google 클라이언트 ID의 환경별 설정을 대조한다. `401` 중 최초 비로그인·access 만료·재발급 불가와 서버 장애를 구분할 근거도 받는다.
- [ ] **계약 확정 후 FE** — 공통 요청과 서버 첫 조회에 인증을 연결한다. 같은 사용자 범위에서 동시에 만료된 요청의 갱신을 공유하고, 재발급 호출의 재귀·무한 재시도 및 결과가 불명확한 쓰기 요청의 자동 재시도를 막는다. `Set-Cookie`의 브라우저 전달, 로그아웃과 갱신 경합, 직접 진입·새로고침·이동에서 원래 목적지 복귀를 검증한다. 현재 로그인 본문 `idToken`과 응답 `id/email/universityVerified`를 기준으로 한다.

#### AUTH-02 · 별도 `.ac.kr` 이메일 인증

- [ ] **FE 선행** — 현재 화면의 삼육대학교 한정 문구와 예시를 `.ac.kr` 대학 이메일 기준으로 바꾸고, Google 로그인 이메일과 입력한 학교 이메일을 별개로 안내한다. 로그인 계정에 도메인 제한을 추가하지 않는다. 문구·입력 상태 스토리를 함께 갱신한다.
- [ ] **BE 선합의** — 현 발송·재발송·검증 명세는 `userId`를 요구하며 FE도 전송한다. 발송 설명은 서버 로그 출력이다. 실제 메일 수신, 로그인 이메일과의 일치 검사 없음, 인증 완료 후 `universityVerified` 재조회, 코드 만료와 재발송 시각·횟수 초과 오류를 확인한 뒤 응답 기준으로 화면을 연결한다. 임의의 고정 타이머를 서버 정책으로 간주하지 않는다.

#### ACCESS-01 · 공개·비공개·소프트 삭제 조회

- [ ] **BE 선합의** — 공개 상세는 비로그인도 가능하고, 비공개 프로젝트는 OWNER/MEMBER, 비공개 포트폴리오는 소유자만 조회할 수 있다. 프로젝트 상세는 상태·공개 여부·요청자 역할과 `401/403/404` 선언이 부족하다. 포트폴리오 slug 상세의 설명에는 비공개 타인 `404`가 있지만 응답 선언은 `200`뿐이다. 비로그인 비공개 상세의 `401/404` 우선순위와 DRAFT의 MEMBER 열람 범위, 소프트 삭제 계정·콘텐츠가 목록·검색·상세·연결 조회에서 제외되는지 확정한다.
- [ ] **계약 확정 후 FE** — 프로젝트 상세 서버 요청에도 쿠키를 전달하고, 포트폴리오 상세와 함께 정상 공개·권한 있는 비공개·타인 `404`·인증 필요·장애를 분리한다. 권한 정보로 편집 진입을 제어하고 보호 데이터가 이전 사용자 캐시나 Mock에 남지 않는지 확인한다. 권한은 서버 응답으로 판정한다.

## 1. 이번 명세에서 실제로 달라진 것

| 대상 | 이전 → 최신 | 교체 판단 |
|---|---|---|
| `POST /api/auth/login` | 서버 세션에 사용자 ID 저장 → JWT를 HttpOnly 쿠키로 발급 | 인증 수명 관리와 쿠키 전달 경로 점검. 요청 `idToken`, 응답 `id/email/universityVerified`는 동일 |
| `POST /api/auth/refresh` | 없음 → Access/Refresh Token 재발급 추가 | 경로·호출·만료 복구 흐름 신규 연결. request body 없음, 성공은 `ApiResponseLoginResponse` |
| `POST /api/auth/logout` | 세션 만료 → Refresh Token 폐기 및 인증 쿠키 삭제 | 사용자 로그아웃 흐름은 기존 미구현. 신규 인증 방식에 맞춰 연결 |
| `POST /api/auth/test-login/{userId}` | 존재 → 명세에서 제거 | 제품 코드 호출은 발견되지 않음. 외부 개발 절차에 남았는지 점검 |
| `MyProjectResponse.tags` | 배열 필드 존재 → 필드 삭제 | 내 프로젝트 DTO·카드·포트폴리오 제작 검색/표시·Mock/스토리 조정 |
| 로그인 및 포트폴리오 상세 오류 선언 | login의 400/401, `GET /api/portfolios/{slug}`의 404 response 선언 삭제 | 오류 처리가 없어졌다는 뜻으로 해석하지 않음. 상세 설명의 비공개 타인 접근 404 정책은 유지돼 명세 보완 필요 |

공통 operation 중 JSON이 달라진 것은 login/logout/slug 조회 3개다. 추가 1개와 삭제 1개를 별도로 집계한다. 공통 schema 중 달라진 것은 `MyProjectResponse` 하나이며 schema 추가·삭제는 없다.

변경된 3개 operation의 200 응답 설명도 ‘로그인 성공’/‘로그아웃 성공’/‘포트폴리오 조회 성공’에서 `OK`로 단순화됐다. 성공 응답 schema 변경은 아니다.

**유지되는 계약:** 홈, 프로젝트 검색·상세·생성·수정·발행, 파일 업로드·목록·삭제, AI 리뷰, 학교 이메일, 사용자, 프로필, 포트폴리오 생성·목록·수정·공개·프로젝트 구성·순서·삭제의 요청/응답 스키마는 이번 비교에서 바뀌지 않았다. 공통 인증 변경에 따른 회귀 검증은 필요하지만 전부 새 API로 교체할 근거는 없다. 프로젝트 상세·검색의 `tags`는 유지되므로 내 프로젝트의 삭제를 전체 도메인에 적용하지 않는다.

## 2. 먼저 확인할 계약 — P0

이 절은 백엔드와 확정할 질문이다. 답이 없는 부분을 프론트 임의 정책이나 가상의 성공 응답으로 채우지 않는다. 각 답변은 후속 명세 또는 합의 근거와 함께 기록한다.

- [ ] **C-01 · JWT 쿠키와 만료 복구 계약:** 쿠키 이름, Domain/Path, SameSite/Secure, 만료 시간, refresh 쿠키 전달 범위, 회전·폐기 방식, access 만료와 인증 없음의 구별, refresh 실패 상태/오류 코드를 확인한다. 현재 `securitySchemes`와 쿠키/응답 헤더 정의가 없다. 브라우저 `/api/*` rewrite와 서버 직접 호출 모두에서 필요한 계약을 확정한다.
- [ ] **C-02 · 현재 사용자 식별 계약:** 아래 필수 `userId` query가 실제 요구사항인지, JWT에서 식별해야 하는지 확인한다. 특히 최초 `GET /api/users/me` 전에 ID를 어떻게 얻는지, 타인의 `userId`를 보냈을 때 서버가 어떻게 권한을 검사하는지 확정한다. `/users/me`와 프로필 설명에는 여전히 세션 문구가 남아 있다. 임의 ID 추가나 명세 query 삭제로 불일치를 숨기지 않는다.
- [ ] **C-03 · 오류 계약:** login 400/401 및 slug 조회 404 선언 누락을 확인하고 공통 오류 schema와 만료/권한/인증 필요 구별을 요청한다. 여러 오류 응답이 성공 schema를 참조하고 공통 wrapper는 `success/data`만 정의한다. 기존 오류 UI를 제거하지 않는다.
- [ ] **C-04 · 내 프로젝트의 정보 범위:** `tags` 미제공이 최종 계약인지 확인한다. 태그 제공이 필요한 화면의 요구사항과 현재 목록의 배열·무query 계약도 함께 확인한다. `description`은 이전부터 목록 schema에 없었다. 추가 상세 조회나 신규 검색 API를 확정한 것으로 기록하지 않는다.

### C-02 대상별 현황

| 명세상 필수 `userId` query 대상 | 현재 프론트 | 후속 조치 |
|---|---|---|
| `GET /api/users/me` | query 생략 | 초기 사용자 조회와 인증 게이트를 확정 계약에 맞춤 |
| `GET/POST/PATCH /api/profile` | query 생략 | 조회·생성·수정 및 관련 스토리 함께 수정 |
| `GET /api/users/me/portfolios` | page/size/isPublic만 전송 | 목록 query와 사용자 식별을 정합화 |
| `POST /api/portfolios`, `PATCH /api/portfolios/{portfolioId}` 및 `/visibility`, `/projects`, `/order` | userId 생략 | 생성부터 후속 저장까지 동일 기준 적용 |
| `DELETE /api/users/me`, `DELETE /api/portfolios/{portfolioId}` | 사용자 행동 미구현 | 구현 시 동일 계약과 권한 검사 적용 |
| `POST /api/auth/email/send`, `/resend`, `/verify` | **이미 userId 전송** | 누락 수정 대상이 아님. 선행 사용자 조회·만료 복구와 함께 검증 |

위 query 차이는 **구버전부터 있던 불일치**이며 JWT 전환으로 자동 해결되지 않는다. 프로젝트 API와 내 프로젝트 목록에는 이 userId query가 정의되어 있지 않다.
